# API 完整规范

本文件保存跨项目 API 设计的详细检查标准和示例。新增接口或修改接口契约时读取；仅修改已有接口内部实现时不加载。

目标项目的真实接口契约、调用方和项目规则优先。发现本规范内部冲突或与项目事实不一致时，不自行选择覆盖关系，应暂停契约修改并确认。

## 路径命名

### 命名服从目标项目契约

采用功能式 lowerCamelCase 的项目可以使用：

```text
getOrderInfo
saveAftersalesInfo
getUserList
submitApproval
```

采用资源式路径的项目可以使用：

```text
/orders/{orderId}
/orders/{orderId}/items
/approval-requests
```

新增路径服从项目已有的大小写、分隔符、资源命名或功能命名约定。同一模块不混用多套风格；已有接口不为统一命名而修改路径。没有明确约定时，先确认接口契约。

### URI 层级

推荐结构：

```text
/{服务标识}/{模块}/{功能}
```

除 `/api`、`/api/v1` 等通用网关或版本前缀外，业务路径通常不超过三层。

```text
/internal/order/getDetail
/api/v2/order/cancel
```

清晰的 RESTful 子资源可以例外，例如 `/api/v1/orders/{orderId}/items`。不得把查询、转换、校验等内部处理步骤暴露为多层 URL。

## HTTP 方法

| 场景 | 方法 |
| --- | --- |
| 读取 | 通常使用 GET，不能执行有副作用的写操作 |
| 参数较多或请求体查询 | 按项目确认的查询协议选择，明确缓存和重试语义 |
| 创建 | 通常使用 POST，沿用项目契约 |
| 更新 | 按完整替换、局部修改或项目约定选择 PUT、PATCH 或 POST |
| 删除 | 按项目契约选择 DELETE 或业务动作接口 |
| 业务动作 | 明确动作语义、幂等要求和项目约定 |

上表是设计参考，不强制迁移既有接口。HTTP 方法、认证、网关和调用方约定应共同确认，不能仅凭局部风格修改契约。

## 请求校验

Java/Spring 项目使用目标项目认可的 Bean Validation：

- 必填对象使用 `@NotNull`，必填字符串使用 `@NotBlank`。
- 长度使用 `@Size`，数值范围使用 `@Min`、`@Max` 或项目认可的约束。
- 格式使用项目已有注解或自定义约束。
- Controller 使用 `@Valid` 或 `@Validated`。

校验职责：

| 校验类型 | 落点 |
| --- | --- |
| 必填、格式、单字段值域 | 请求模型 |
| 只依赖请求字段的组合规则 | 请求对象的语义方法或组合约束 |
| 数据库存在性 | 业务层 |
| 当前用户权限 | 业务层或权限边界 |
| 业务状态是否允许操作 | 业务层 |

已有边界校验可靠覆盖后，Service 不重复判断相同的必填和格式约束。请求字段应符合调用方真实掌握的数据；调用方只有 `code` 时，不要求其为了服务端内部模型提前转换为 `id`。

## 响应结构和错误码

接口复用目标项目现有响应结构，不在局部重新定义统一包装器；已有响应模型继续复用项目实际字段和构造方法，不根据示例重新实现一份响应类。

HTTP 状态和业务码的关系以目标项目为准：

- 不强制所有项目采用相同业务码。
- 不强制改变已经稳定的 HTTP 200 加业务码契约。
- 新接口不得同时混用两套未经确认的错误码体系。
- 客户端文案与服务端诊断信息分离。

错误响应不得暴露数据库连接、SQL、堆栈、内部路径和未经筛选的异常消息。

## 分页、过滤和排序

可能持续增长的列表应分页。分页模型复用项目已有结构，并明确：

- 页码从 0 还是 1 开始。
- 页大小和最大值。
- 总记录数、总页数或 `hasMore`。
- 默认排序字段。
- 相同排序值下的稳定次序。

数据库分页必须具有稳定排序，避免翻页过程中出现重复或遗漏。过滤字段和排序字段使用明确白名单，不能直接把外部输入拼入 SQL。

明确有界的小型字典、枚举和配置集合可以不分页。

## 认证和授权

新增接口必须明确是否允许匿名访问。认证表示“当前调用者是谁”，授权表示“当前调用者能否操作目标资源”，不能只做认证而遗漏授权。

复用目标项目已有认证设施，不自行实现 Token 加密、密码算法或身份解析协议。

身份可能由 Session、Token 或受信任网关传递。必须根据目标项目的真实认证链路确认信任边界，不能把调用方自行提交的 Header 当成可信身份，也不能仅根据本规范创建身份协议。

请求结束后，项目使用的 ThreadLocal 身份上下文必须按既有机制清理。

## 接口兼容

以下通常属于破坏性变化：

- 删除或重命名字段。
- 修改字段类型。
- 可选字段改为必填。
- 修改空值或默认值语义。
- 修改 URL 或 HTTP 方法。
- 修改认证方式。
- 修改错误码、分页、过滤或排序语义。

新增可选响应字段、可选查询条件或独立端点通常可以兼容，但仍需确认直接调用方。

是否需要新版本、灰度或兼容字段，根据真实调用方和项目发布策略确定，不使用固定时间线替代项目决策。

## Feign 契约

Feign 方法、路径、请求响应模型和降级行为服从远程服务。修改 Feign 时检查：

- URL 和 HTTP 方法是否与远程接口一致。
- 参数位置、字段名和序列化方式是否一致。
- 响应包装和错误码是否一致。
- null、空列表和异常的语义是否保持。
- 是否意外新增告警、重试或降级副作用。

不使用本规范的新接口命名和路径规则改写远程契约。

## OpenAPI/Swagger

新增接口和契约变化应同步：

- 方法和路径。
- 请求字段、类型和必填性。
- 响应字段和空值语义。
- 错误响应。
- 认证要求。
- 分页、过滤和排序参数。
- 字段说明及必要示例。

只修改内部实现且接口契约没有变化时，不机械修改接口文档。
