# API 设计与兼容规范

本 Skill 适用于 Controller、请求/响应模型、OpenAPI/Swagger，以及涉及接口契约的相关代码。

目标项目的既有接口、真实调用方和项目规则优先。不得为了统一新接口风格修改已发布契约。

处理边界：

- 新增接口执行完整设计规范。
- 修改已有接口契约时只检查本次变化、兼容性和文档，不改造未触达的历史风格。
- 仅修改已有接口内部实现时保持原契约，只检查安全、错误处理和本次代码质量。

## 加载方式

仅修改已有接口内部实现，且没有改变 URL、HTTP 方法、请求响应、认证、错误码、分页和接口文档时，只执行本文件中的核心规则。

出现以下任一情况时，必须同时读取 [完整 API 规范](references/api-spec.md)：

- 新增接口。
- 修改 URL、HTTP 方法或接口注解。
- 新增、删除或修改请求响应字段。
- 修改字段类型、必填、空值或默认值语义。
- 修改分页、过滤、排序、认证、授权、响应结构或错误码。
- 修改 OpenAPI/Swagger。
- 现有项目口径不明确或存在冲突。

纯 Service、Domain 或 Repository 修改不涉及接口契约时，不加载本 Skill。

## Feign 边界

Feign 是远程接口契约的消费者：

- 不执行新增接口的命名、路径层级和 HTTP 方法风格检查。
- 不因本 Skill 改写远程服务已有 URL、方法、字段或响应结构。
- 只检查本次改动是否保持远程契约、异常处理、安全错误和既有降级语义。
- 远程契约不明确时，查询真实接口或咨询用户，不按本地风格推断。

## [MUST] api.follow-project-path-conventions

新增接口的资源名、功能段、大小写和分隔符遵循目标项目已确认的命名约定。同一模块保持一致，不把某种 REST 或 RPC 风格强制覆盖到所有项目。

适用边界：只约束新增 Controller 和同步新增的 OpenAPI/Swagger 契约；不扫描 Feign，不为统一风格修改已发布接口路径；清晰的 RESTful 子资源路径服从目标项目既有约定。

## [SHOULD] api.business-path-depth

除 `/api`、版本号等通用前缀外，新增业务路径通常不超过三层。确有清晰子资源关系时可以更深，但不得把内部处理步骤逐层暴露到 URL。

## [MUST] api.follow-project-http-method-policy

HTTP 方法遵循目标项目的接口策略和操作语义。GET 不执行有副作用的写操作；创建、更新、删除、复杂查询和业务动作应与现有调用方、网关及客户端约定一致。项目未定义时，先确认契约，不默认把所有写操作统一成 POST，也不为统一风格修改已有方法。

## [MUST] api.validate-request-boundary

新增或修改外部输入时，必须在请求边界完成必填、格式和单字段值域校验。

只依赖请求自身字段的组合校验，可以由请求对象提供有业务语义的方法；涉及数据库、权限和业务状态的校验留在业务层。已有边界校验可靠覆盖后，后续层不重复进行基础合法性校验。

详细注解和示例参见完整规范的“请求校验”。

## [SHOULD] api.use-project-response-envelope

新增接口复用目标项目现有的统一响应结构，不局部发明新的包装器、错误字段或错误码数值表；项目没有统一包装时，沿用已经确认的协议契约。

## [SHOULD] api.paginate-list-endpoints

可能持续增长的集合接口使用项目统一分页模型，并明确页码起点、每页大小、总记录数或下一页判断，以及稳定排序方式。明确有界的字典、枚举或配置集合可以不分页。

## [MUST] api.enforce-auth-boundary

新增接口必须明确属于需要认证和授权、只需要认证或经确认允许公开访问中的哪一种。

需要认证的接口复用项目现有身份上下文和认证设施；需要授权的接口检查当前用户对目标资源或业务动作的权限。不得因为请求携带用户 ID、组织 ID 或 Header 就默认其已经获得授权。

## [MUST] api.preserve-published-contract

修改 URL、HTTP 方法、请求响应字段、字段类型、必填性、空值、默认值、认证方式、权限语义、错误码、响应结构、分页、过滤或排序语义前，必须确认调用方、版本和兼容策略。

新增可选响应字段通常可以兼容，但仍需同步直接相关的接口文档。Feign 以远程服务当前契约为准，不因本 Skill 的新接口风格改写方法、路径、字段或降级语义。

## [MUST] api.no-internal-error-details

接口响应不得返回堆栈、SQL、内部路径、凭据、未经筛选的异常消息或其他只应出现在服务端日志中的诊断信息。详细上下文保留在经过脱敏的服务端日志中。

## [MUST] api.sync-contract-docs

新增接口或发生接口契约变化时，必须同步直接相关的 OpenAPI/Swagger 和接口说明。仅修改内部实现且契约没有变化时，不机械修改接口文档。

## 修复边界

新接口命名、明确的基础校验、内部错误泄露、契约文档遗漏，以及新增无语义包装或重复转换等问题，可以直接完成最小修复。

涉及已发布接口、Feign、字段业务语义、认证授权、错误码或调用方影响，且存在多种合理选择时，先整理差异和影响，再询问用户。不以本 Skill 为由批量格式化或迁移历史接口。

## API 变更完成前检查

- [ ] 已确认本次属于内部实现调整、新增接口还是契约变更；需要时已读取完整规范。
- [ ] 新增接口命名、路径和 HTTP 方法满足对应正式规则。
- [ ] 新增或修改的外部输入满足 `api.validate-request-boundary`。
- [ ] 响应复用项目现有契约，没有新增无语义包装层。
- [ ] 增长型列表满足 `api.paginate-list-endpoints`。
- [ ] 认证和授权满足 `api.enforce-auth-boundary`。
- [ ] 已发布契约满足 `api.preserve-published-contract`，Feign 未被套用新增接口风格。
- [ ] 错误响应满足 `api.no-internal-error-details`。
- [ ] 契约变化已按 `api.sync-contract-docs` 同步文档。
- [ ] 请求字段符合调用方真实掌握的数据，没有把服务端内部转换责任推给调用方。
- [ ] 请求语义一致时直接传递 Req，没有机械拆成多个基础参数。
- [ ] 简单响应直接返回，复杂响应一次性组装，没有无业务语义的中间对象。
